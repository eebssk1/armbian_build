U:bcm43456 5ghz disabled in china
A:If your Broadcom BCM43456 Wi-Fi chip (commonly found in devices like the Raspberry Pi 4 or Raspberry Pi 400) is failing to detect or connect to 5GHz Wi-Fi networks when the regulatory country code is set to China (https://www.google.com/search?kgmid=%2Fm%2F0d05w3) (CN), the issue is caused by a restrictive conflict within the brcmfmac firmware or the local wireless domain configurations. [1] (https://github.com/raspberrypi/firmware/issues/1246), [2] (https://github.com/raspberrypi/firmware/issues/1359)

Why This Happens

China utilizes specific subsets of the 5GHz spectrum. In older regulatory tables or certain clm_blob (Country Locale Matrix) firmware files associated with Broadcom chips, setting the region to CN defaults to restrictive channel profiles. Often, the firmware either: [1] (https://silexamerica.my.site.com/s/article/Understanding-Wireless-Regulations-in-China), [2] (https://blog.csdn.net/weixin_26886855/article/details/166344785), [3] (https://github.com/raspberrypi/firmware/issues/1359)
1. Disables 5GHz entirely due to a fallback misconfiguration (DFS-UNSET).
2. Restricts 5GHz scanning strictly to channels 149 and above (5745–5825 MHz), completely ignoring lower 5GHz bands like channels 36–64 (5150–5350 MHz) even though Chinese regulations technically permit them. [1] (https://forums.raspberrypi.com/viewtopic.php?t=389452), [2] (https://silexamerica.my.site.com/s/article/Understanding-Wireless-Regulations-in-China), [3] (https://github.com/raspberrypi/firmware/issues/1359)

How to Fix It


1. Shift Your Router's 5GHz Channel

If you want to keep your device set to the CN regulatory domain, log into your Wi-Fi router's admin panel and manually switch your 5GHz channel to a higher index permitted by China's wireless table: [1] (https://github.com/raspberrypi/firmware/issues/1246)
• Supported Chinese 5GHz Channels: 149, 153, 157, 161, or 165 [1] (https://github.com/raspberrypi/firmware/issues/1246)

2. Set an Overriding Regulatory Country Code

If your router is outputting on lower 5GHz bands and you cannot change its channels, you can set your operating system's wireless region to a territory with overlapping or broader 5GHz channel mappings (such as the US or a global profile) to force the driver to look for those frequencies. [1] (https://forums.raspberrypi.com/viewtopic.php?t=388494)
• Temporary change (Linux / Raspberry Pi CLI):bash
sudo iw reg set US
Use code with caution.
• Permanent change (Raspberry Pi OS):
Run sudo raspi-config, navigate to Localisation Options -> WLAN Country, and adjust the territory from CN to US or GB. [1] (https://forums.raspberrypi.com/viewtopic.php?t=388494)

3. Update Firmware and Regulatory Database Files

If you are running an alternative Linux distribution (like OpenWrt, AlmaLinux, or Ubuntu Core), your operating system might lack the required signatures to decrypt or enforce local 5GHz domains. Installing or updating the full local wireless regulatory database will often solve this: [1] (https://www.reddit.com/r/AlmaLinux/comments/1mzmzf0/almalinux_10_on_raspberry_5_no_5ghz_band_cant_set/), [2] (https://forums.raspberrypi.com/viewtopic.php?t=389452), [3] (https://github.com/raspberrypi/firmware/issues/1246)
bash
# On Debian/Ubuntu/Raspberry Pi OS:
sudo apt update && sudo apt install --reinstall wireless-regdb crda

# On Fedora/RHEL/CentOS:
sudo dnf reinstall wireless-regdb
Use code with caution.
Additionally, make sure you copy or update the matching brcmfmac43456-sdio.clm_blob and binary configurations into your /lib/firmware/brcm/ directory. The official Raspberry Pi Firmware GitHub Repository hosts updated files that correctly allow simultaneous 2.4GHz and 5GHz operations. [1] (https://discussion.fedoraproject.org/t/wifi-5ghz-not-showing-f40-broadcom/130537), [2] (https://github.com/AlmaLinux/raspberry-pi/issues/23), [3] (https://github.com/raspberrypi/firmware/issues/1359)
To help pinpoint the issue, please share:
• What operating system (e.g., Raspberry Pi OS, OpenWrt, Ubuntu) you are currently running.
• What channel number your 5GHz Wi-Fi network uses.
• The output of running iw dev wlan0 scan or iw reg get in your terminal.

1. Edit the Broadcom NVRAM Text File (Most Likely Cause)

On Armbian (especially on SBCs made by Chinese manufacturers like Orange Pi, Radxa, or NanoPi), the board's specific NVRAM calibration file usually has ccode=CN hardcoded into it. Every time the kernel loads the brcmfmac module at boot, it forces the chip into the CN region.
1. Find the active NVRAM .txt file in the Broadcom firmware folder:bash
grep -rn "ccode=" /lib/firmware/brcm/ /lib/firmware/updates/brcm/ 2>/dev/null
Use code with caution.
(Look for files named brcmfmac43456-sdio.txt or brcmfmac43456-sdio.<board-name>.txt.)
2. Open the matching file(s) with a text editor:bash
sudo nano /lib/firmware/brcm/brcmfmac43456-sdio.txt
Use code with caution.
(If there is a board-specific file like brcmfmac43456-sdio.radxa,zero3.txt, edit that one too).
3. Change the country code lines inside the file:
	• Find ccode=CN (or ccode=ALL / ccode=0) and change it to:ini
ccode=US
Use code with caution.
	• Find regrev= and ensure it is set to 0:ini
regrev=0
Use code with caution.
4. Save and exit (Ctrl+O, Enter, Ctrl+X).

2. Lock the Kernel Regulatory Domain

Modern kernels used in Armbian Trunk pass the regulatory domain directly via the cfg80211 kernel module.

Use code with caution.
2. Check legacy CRDA config (if present on your Debian/Ubuntu base):
If the file /etc/default/crda exists, open it (sudo nano /etc/default/crda) and ensure it says REGDOMAIN=US.
3. Update the initramfs so the setting applies early in the boot process:bash

Use code with caution.

3. Check wpa_supplicant Overrides

If you previously configured Wi-Fi via armbian-config or manually, wpa_supplicant might have saved country=CN in its config and is pushing it to the driver when NetworkManager initializes.
1. Check if any wpa_supplicant file has a country code set:bash

Use code with caution.
2. If you find a file containing country=CN, open it and change it to country=US.

Test the Fix

Reboot your board (sudo reboot) and run:
bash
iw reg get
Use code with caution.
It should now persistently show country US: DFS-FCC across both global and phy#0.

Because FullMAC Broadcom chips (brcmfmac / bcmdhd) manage their own regulatory state inside the ARM Cortex-R4/M3 processor on the Wi-Fi module, standard Linux regulatory.db changes do not control the firmware's internal channel table. Instead, the driver sends the "country" IOVAR down the SDIO bus to the chip, or the chip's internal autocountry feature parses the 802.11d IE directly from incoming frames.
Apply one of these three firmware-level fixes:

1. Disable Firmware-Level 802.11d / Auto-Country via wl or IOVAR

Broadcom firmware has internal IOVARs (autocountry and 11d) that tell the chip's microprocessor whether to adopt country codes from AP beacons on its own.
• In your NVRAM file (/lib/firmware/brcm/brcmfmac43456-sdio.txt):
Add these lines alongside ccode=US to tell the firmware state machine not to auto-switch:ini
autocountry=0
11d=0
Use code with caution.
• In the kernel driver (when initializing the chip):
Send the IOVAR command down to the firmware during brcmf_cfg80211_attach (for brcmfmac) or dhd_preinit_ioctls (for bcmdhd):
	• brcmfmac:c
brcmf_fil_iovar_int_set(ifp, "autocountry", 0);
brcmf_fil_bsscfg_int_set(ifp, "11d", 0);
Use code with caution.
	• bcmdhd:c
dhd_wl_ioctl_set_intiovar(dhd, "autocountry", 0, WLC_SET_VAR, TRUE, 0);
Use code with caution.

2. Hardcode "US" in the Driver's Firmware IOVAR Call

Even when the request starts as a user-land/cfg80211 notification (Request regdom change mode = CountryIE), the driver translates that notification into a firmware IOVAR command ("country" / WLC_SET_COUNTRY) that physically alters the firmware's running CCode (Firmware changed CCode to CN).

• If using bcmdhd (wl_cfg80211.c / dhd_common.c):

Use code with caution.
• If using brcmfmac (cfg80211.c):
In brcmf_cfg80211_reg_notifier, the driver calls brcmf_fil_iovar_data_set(ifp, "country", &ccreq, sizeof(ccreq)). That exact line is what changes the firmware's internal state. A:To stop brcmfmac from overriding your country code to CN upon receiving 802.11d beacons, you must either patch the brcmfmac kernel module (in cfg80211.c), binary-patch the CN string out of your firmware binary, or add a country_codes translation table via Device Tree.

Why modprobe and .txt Edits Failed

1. cfg80211 ignores ieee80211_regdom=US once connected: When brcmfmac registers with the Linux kernel (wiphy), it does not set the REGULATORY_COUNTRY_IE_IGNORE flag. As soon as wpa_supplicant associates with your AP, the kernel's cfg80211 parses the AP's 802.11d beacon (mode = CountryIE) and calls brcmf_cfg80211_reg_notifier().
2. brcmf_cfg80211_reg_notifier() pushes CN into the firmware: Inside drivers/net/wireless/broadcom/brcm80211/brcmfmac/cfg80211.c, the driver takes req->alpha2 ("CN") and sends brcmf_fil_iovar_data_set(ifp, "country", &ccreq, sizeof(ccreq)) straight over the SDIO bus into the chip.
3. NVRAM .txt only sets initial state: The .txt file only initializes NVRAM variables in RAM at power-up; it cannot block runtime IOVAR commands from the host driver.

Fix 1: Binary-Patch "CN" in the Firmware / CLM Blob (Zero Recompile)

When brcmfmac sends the "country" IOVAR with "CN" to the chip, the firmware looks up "CN" inside its internal Country Locale Matrix (either in brcmfmac43456-sdio.clm_blob or embedded inside brcmfmac43456-sdio.bin). If the firmware cannot find "CN" in its table, it rejects the country change (Firmware rejected country setting) and stays on US!
Alternatively, you can replace the broken CN channel list by installing the updated Synaptics/Raspberry Pi 400 clm_blob and .bin files:

Option A: Hex-edit the firmware so it rejects "CN"

1. Check if your firmware uses an external .clm_blob or embeds it in .bin:bash
ls -la /lib/firmware/brcm/*43456*
Use code with caution.
2. Back up your firmware files:bash
cp /lib/firmware/brcm/brcmfmac43456-sdio.bin /root/brcmfmac43456-sdio.bin.bak
cp /lib/firmware/brcm/brcmfmac43456-sdio.clm_blob /root/brcmfmac43456-sdio.clm_blob.bak 2>/dev/null
Use code with caution.
3. Run this Python one-liner to replace the "CN\x00" country table entries in the binary/blob with "C9\x00" (a dummy code that never matches "CN"):bash
python3 -c '
import glob
for path in glob.glob("/lib/firmware/brcm/*43456*.bin") + glob.glob("/lib/firmware/brcm/*43456*.clm_blob"):
    with open(path, "rb") as f:
        data = f.read()

Use code with caution.

A:Since you are building your own image with an Armbian userpatches overlay, the cleanest, permanent fix is to add a small kernel patch to userpatches/kernel/<your-kernel-family>/ that blocks brcmfmac from ever passing "CN" or CountryIE requests down to the firmware.
Here are the two exact ways to solve this—either cleanly in your Armbian build patch, or immediately on your live board without rebuilding.

Method 1: Add a Kernel Patch to Your Armbian userpatches (Permanent Build Fix)

In drivers/net/wireless/broadcom/brcm80211/brcmfmac/cfg80211.c, you can both tell the Linux kernel's wiphy layer to ignore 802.11d beacons (REGULATORY_COUNTRY_IE_IGNORE) and intercept any "CN" request inside brcmf_cfg80211_reg_notifier() so it translates "CN" into "US" before calling the firmware's "country" IOVAR.
Drop this patch into your Armbian userpatches/kernel/<family>-<branch>/ folder (e.g., zzz-brcmfmac-ignore-country-ie.patch):
diff
--- a/drivers/net/wireless/broadcom/brcm80211/brcmfmac/cfg80211.c
+++ b/drivers/net/wireless/broadcom/brcm80211/brcmfmac/cfg80211.c
@@ -7800,6 +7800,14 @@ static void brcmf_cfg80211_reg_notifier(struct wiphy *wiphy,
 	struct brcmf_if *ifp = brcmf_get_ifp(cfg->pub, 0);
 	struct brcmf_fil_country_le ccreq;
 	s32 err;
+
+	/* Ignore 802.11d AP Country IE updates completely */
+	if (req->initiator == NL80211_REGDOM_SET_BY_COUNTRY_IE)
+		return;
+
+	/* Force CN requests to US */
+	if (req->alpha2[0] == 'C' && req->alpha2[1] == 'N') {
+		req->alpha2[0] = 'U';
+		req->alpha2[1] = 'S';
+	}
 
 	/* ignore non-ISO3166 country codes */
 	for (i = 0; i < 2; i++)
@@ -8020,6 +8028,7 @@ struct brcmf_cfg80211_info *brcmf_cfg80211_attach(struct brcmf_pub *drvr,
 	wiphy->regulatory_flags |= REGULATORY_CUSTOM_REG;
+	wiphy->regulatory_flags |= REGULATORY_COUNTRY_IE_IGNORE;
Use code with caution.
(Note: Since you already added the [T89] Request regdom change debug print inside your kernel tree, you can place those two if blocks right at the top of the exact function where you put your printk/pr_info!)

Method 2: Why the Updated clm_blob Didn't Fix 5GHz (And How to Fix It Live)

There is a critical quirk with the AP6256 (BCM43456) firmware (brcmfmac43456-sdio.bin):
1. BCM43456 firmware Often Ignores External .clm_blob Files: Unlike the BCM43455 (which requires an external .clm_blob), most AP6256 / BCM43456 .bin firmware builds have their CLM table statically compiled inside brcmfmac43456-sdio.bin and don't even request brcmfmac43456-sdio.clm_blob from the kernel (you can verify this by checking dmesg | grep -i clm).
2. Even if loaded, CN in the CLM table defaults to regrev=0 or DFS-FCC with NO-IR: When brcmfmac switches to CN (ccode=CN, regrev=0 or -1), the internal table inside brcmfmac43456-sdio.bin disables channels 36–144 unless a specific high regrev (like CN/38) is requested.

Instant Live Fix on the Board (No Recompile Needed)

Since your NVRAM .txt already boots the firmware into US ([ 18.290924] Firmware current CCode is US), you can stop brcmfmac.ko from ever changing the firmware's country code after boot by patching the "country" IOVAR string inside brcmfmac.ko on your live system:
bash
# 1. Locate the brcmfmac kernel module
MOD=$(modinfo -n brcmfmac)
cp "$MOD" /root/brcmfmac.ko.bak

# 2. Replace the "country\0" IOVAR string with "countrx\0" so post-boot CCode changes fail harmlessly
python3 -c "
p = '$MOD'
with open(p, 'rb') as f: d = f.read()
assert b'country\x00' in d, 'String not found (module may be compressed)'
with open(p, 'wb') as f: f.write(d.replace(b'country\x00', b'countrx\x00'))
print('Successfully locked brcmfmac to boot NVRAM ccode!')
"

# 3. Reload the module
modprobe -r brcmfmac_wcc brcmfmac 2>/dev/null; modprobe brcmfmac
Use code with caution.
With "country\x00" changed to "countrx\x00", the chip boots up with ccode=US from your brcmfmac43456-sdio.txt, and when the router's CountryIE triggers at 18 seconds, the countrx IOVAR returns -23 (BCME_UNSUPPORTED) and leaves the firmware permanently on US.
